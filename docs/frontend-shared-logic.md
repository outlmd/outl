# `@outl/shared`: the pure helpers

Every pure function in the shared library, with the Rust source each one mirrors.

Moved out of [`crates/outl-frontend-shared/CLAUDE.md`](../crates/outl-frontend-shared/CLAUDE.md), which is loaded into the model's context on every session in that crate.
The catalog is reference: you look an entry up before writing a helper, you do not read it top to bottom.
The decision rule for what may enter the library stayed in that file.

The surface is three pages, so grep all of them at once: `grep -n 'symbol' docs/frontend-shared-*.md`.

| Page | What it lists |

| [`frontend-shared-views.md`](frontend-shared-views.md) | Components and the view pieces both clients render |

| `caretExit(key, text, start, end)` → `CaretExit \| null` and `resolveCaretExit(blocks, id, exit)` → `CaretLandingTarget \| null` — **cross-block caret nav in Insert mode**: the outline reads as one continuous document, so `←` at offset 0 lands at the end of the block above, `→` at the end lands at the start of the one below, and `↑` / `↓` on the block's first / last line carry the column over. The one owner of both halves — *does this keystroke leave the block* and *which block does it hand the caret to* — so what a client keeps is only what it alone knows: which blocks are on screen, and how it enters Insert. Three rules worth not undoing. Offsets are **codepoints** (convert with `utf16OffsetToCharOffset` on the way in); a non-empty selection always answers `null`, because an arrow collapses a selection in place on every platform and hijacking that would make the first arrow after a drag jump to another block; and `resolveCaretExit` indexes `flattenVisible` rather than calling `nextVisibleId` / `previousVisibleId`, because those read a missing id as *the first block* — so a block a peer deleted mid-edit would teleport the caret to the top of the page. `CaretLandingTarget` carries the neighbour's **wire text** beside the offset, because the offset was measured against it: a client that re-fetched the block and seeded its editor from the DTO's split `text` would land the caret a `TODO ` short. **A line here is a logical `\n` line, never a soft-wrapped visual one** — the same rule the TUI ships, and the module doc carries why both alternatives are worse | `@outl/shared/caret-nav` | `outl_tui::input::{cross_block_nav_eligible, cross_block_step}` + `EditBuffer::move_up` / `move_down` |

| `createPageKey(page, select, equals?)` — **the one owner of "did the open page change?"**. Every client replaces the page object on *every* reply, mutations included (`applyPageState` / `applyView`), so a tracked source read straight off it fires on each keystroke-commit — and **`on()` does not stop that**: it makes a dependency explicit and never compares values. This is a `createMemo` with a name, `undefined` while no page is open (which also keeps a `createResource` idle). It exists because the rule was documented and false: the desktop's backlinks fetch blanked its rows and unmounted the section for an `O(blocks-in-workspace)` scan on every block created or deleted, and its sidebar rewrote `localStorage` synchronously on every commit — both under `on(() => appState.page?.slug, …)`, one of them under a comment claiming it fired once per navigation. **Do not reach for it when the effect must re-run on every reply and only *behave* differently on a real change** (`installPageChangeEffect` repairs a stale selection when the outline lands); the file's own doc owns that distinction. `page-key.parity.test.ts` is the net, and it reads **both clients' sources**: the shape is refused on its own, with a declared exception per file and a reason | `@outl/shared/navigation` (`src/navigation/page-key.ts`) | no Rust mirror — Solid reactivity only |
